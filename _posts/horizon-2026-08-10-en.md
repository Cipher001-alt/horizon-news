## [SMM Attack via Extremely Long Interrupt Instruction](https://github.com/xoreaxeaxeax/smiiiiiiiiiiiiiiii) ⭐️ 8.0/10

A security researcher has demonstrated a novel attack technique that exploits System Management Mode (SMM) by using an exceptionally long interrupt instruction, as detailed in the GitHub repository 'smiiiiiiiiiiiiiiii'. This method breaks the secure, ultra-privileged execution environment of x86 CPUs without requiring traditional vulnerabilities. This finding is significant because SMM is a critical security boundary in modern CPUs, and bypassing it could allow attackers to compromise firmware and bypass security mechanisms like UEFI Secure Boot. It highlights a fundamental design weakness that could affect a wide range of systems, prompting a need for updated mitigation strategies. The attack relies on the fact that SMM interrupts are serviced between instructions, and a sufficiently long instruction can cause the CPU to enter SMM while the instruction is still executing, leading to unexpected behavior. The repository includes a proof-of-concept and references related work on instruction latency, such as the 'asm-hall-of-shame' project.

hackernews · WhiteDawn · Aug 10, 16:03 · [Discussion](https://news.ycombinator.com/item?id=49245491)

**Background**: System Management Mode (SMM) is a special CPU mode used for low-level system functions like power management and hardware control. It operates in a separate memory region (SMRAM) and is typically invisible to the operating system and hypervisor. Interrupts called System Management Interrupts (SMIs) trigger entry into SMM, and they are serviced between instructions. This attack exploits the timing of SMI handling with an extremely long instruction, potentially allowing an attacker to manipulate SMM execution.

Simon Willison prototyped storing text revision histories in SQLite by compressing full JSON arrays of prior versions with zlib or zstd. In a 1,000-revision test, 20.4 MB of raw snapshots compressed to 80.3 KB using Zstandard, a 250x reduction. This approach offers a simple yet effective way to store revision histories in relational databases, potentially reducing storage costs and simplifying schema design. It could benefit applications that need versioning for documents, notes, or code snippets without complex delta-encoding logic. To avoid decompressing and recompressing the entire array on every edit, the prototype splits history into multiple rows, each capped at 128 revisions or 3MB of uncompressed JSON. The implementation includes two stores: WholeBlobHistoryStore and ChunkedHistoryStore, with the latter sealing compressed chunks for better scaling.

rss · Simon Willison — AI工具 · Aug 9, 22:05

**Background**: Storing revision histories in relational databases is challenging because naive approaches (one row per version) can quickly bloat storage. Compression algorithms like zlib and Zstandard (zstd) are well-known for reducing data size, and Zstandard offers a good balance of speed and ratio. By compressing a JSON array of all previous snapshots, the compressor effectively acts as an implicit delta encoder, exploiting redundancy across versions.
